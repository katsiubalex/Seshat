# Правила разработки «Сешат»

Обязательны для всех, кто меняет репозиторий: людей и ИИ-агентов. Нарушение любого правила из разделов 1–4 — основание отклонить PR без обсуждения. `CLAUDE.md` — ссылка на этот файл.

Перед началом работы прочитать: этот файл, [ARCHITECTURE.md](ARCHITECTURE.md), [CONTRIBUTING.md](CONTRIBUTING.md) (правила контента), задачу (Issue), из которой идёт работа.

## 0. Роли

- **Заказчик** — автор проекта. Ставит задачу, принимает результат по сайту и контрольным расчётам, не по diff.
- **Исполнитель** — агент или разработчик. Работает только в рамках задачи, сам задачу не расширяет.
- **Куратор / рецензент** — проверяет контент по существу (см. CONTRIBUTING).

## 1. Инженерная честность (главное)

1. **Каждое число имеет источник.** Коэффициент, норматив, цена, формула — рядом ссылка на пункт нормы, страницу издания или расчёт. В коде — комментарий `// СП 32 п. 9.2.5.7` или `// ИТС 10-2019, с. 214`; в статьях — сноска `[^n]`. Число без источника помечается явно (`EST`, `≈`, `[^?]`) и считается долгом.
2. **Не выдумывать.** Если источника нет — написать «источника нет», не подбирать правдоподобное значение. Если норма неизвестна — не угадывать номер пункта.
3. **Тексты норм — по правовому статусу документа** (реестр `legal_status` в паспортах, ADR-007). Официальные акты (законы, постановления Правительства, приказы ведомств и их приложения) публикуются полным текстом с официального источника и пометкой «неофициальная публикация, сверено ДД.ММ.ГГГГ». Для СП, ГОСТ Р и ИТС, пока статус не подтверждён юристом или правообладателем, — структура, номера пунктов и страниц, формулы как методы, собственный пересказ, короткие цитаты. Сводные редакции третьих сторон не публикуются. Учебники — только цитаты и пересказ со ссылкой (ст. 1274 ГК РФ), никаких сканов и глав.
4. **Расчёт прозрачен.** Любое число на экране пользователь может раскрыть до формулы и источника. Новая функция расчёта без объяснения в интерфейсе или в статье не принимается.
5. **Нейтральность.** Ранжирование, подсказки и сравнения — только по объективным критериям. Упоминание производителя или товара — с пометкой, если есть спонсорство или конфликт интересов.
6. **Честные статусы.** Статус материала (`draft`/`auto`/`expert`) и модуля (`ready`/`stub`) меняет только тот, кто имеет на это право; экспертная проверка записывается отдельным коммитом от правки материала.

## 2. Границы задачи

7. **Одна задача — одна ветка — один PR.** Ветка от свежего `main`, имя латиницей по смыслу (`kb-sludge-age`, `fix-ncs-k14`). PR закрывает одну задачу и ссылается на неё («Закрывает #N»).
8. **Не расширять задачу.** Замеченное по пути — отдельная задача (Issue), не правка в этом же PR. Исключение: правка нужна, чтобы задача вообще выполнилась; тогда она названа в описании PR.
9. **Не трогать чужое.** Файлы, не названные в задаче, не меняются, кроме обязательных сопутствующих (`CHANGELOG.md`, `index.html` при подключении скрипта, `ARCHITECTURE.md` при новом файле).
10. **Не удалять без задачи.** Удаление файла, статьи, функции, поля данных — только если задача говорит об этом прямо. Переименование = удаление.
11. **Не переписывать.** Рефакторинг «ради чистоты» без задачи запрещён. Файл меняется минимально необходимым образом; стиль соседнего кода сохраняется.
12. **Не менять интерфейс пользователя** (расположение, названия, цвета) без указания в задаче.

## 3. Данные и совместимость

13. **Формат сохранённых данных — контракт.** Любое изменение схемы проекта, схемы станции, сети, библиотеки сопровождается: `VERSION += 1` в `store.js`, миграцией со старого формата, тестом миграции на реальном старом примере. Пользователь не должен потерять сохранённое.
14. **`id` неизменны.** Идентификаторы сооружений, процессов, показателей, документов, статей (`UNITS[].id`, `content/**/<id>.md`) не переименовываются: на них ссылки, сохранённые схемы и внешние адреса `#kb-…`. Нужен новый смысл — новый `id`, старый остаётся с пометкой.
15. **Генерируемое не правится руками.** `js/content.js` собирается из `content/`; правка — в Markdown, затем `node tools/build-content.js`. Коммитится и источник, и результат сборки.
16. **Данные без логики, логика без DOM.** Файлы данных (`data.js`, `docs.js`…) — только константы. Ядро (`model.js`, `netcalc.js`…) — чистые функции, работающие в Node. Вид — единственное место для `document`, `localStorage`, `fetch`.
17. **Внешние зависимости — через решение.** Новая библиотека, CDN, сервис, сборщик — только через ADR в `docs/decisions/` и одобрение заказчика. Сейчас внешних зависимостей нет (KaTeX — локальная копия), и это намеренно (ADR-001).
18. **Персональные данные не собираются.** Ни форм с email/телефоном, ни аналитики с идентификацией пользователя без отдельного решения. Аналитика — только без куки и без персональных данных.

## 4. Качество кода и проверка

19. **Тест на каждое число.** Новая функция расчёта или изменение коэффициента — тест с контрольным примером из источника (пример из СП, таблица ИТС, расчёт вручную в комментарии). Тест пишется до кода.
20. **`npm test` зелёный.** Перед коммитом: `node tools/build-content.js && npm test`. Красный тест не «чинится» ослаблением проверки.
21. **Тест не удаляется и не ослабляется** без указания в задаче и объяснения в PR.
22. **Версия на каждый PR с изменением кода или контента, видимого на сайте:** `version` в `package.json`, `version.json`, `?v=` во всех HTML (`release.test.js` проверяет); строка в `CHANGELOG.md`; тег `vX.Y.Z` ставит GitHub Actions автоматически после слияния в `main` (`.github/workflows/tag.yml`). Правила номера: `0.X.0` — новая возможность или раздел, `0.X.Y` — исправление; `1.0.0` — ворота этапа 1 (см. ROADMAP).
23. **Новый файл `js/*.js`** — описан в `ARCHITECTURE.md` (тест `architecture.test.js`), подключён во всех HTML, где используется, экспортирует `module.exports` если содержит логику.
24. **Браузерная совместимость:** без сборки, поэтому только синтаксис, который работает в браузерах последних двух лет без транспиляции; никаких `import`/`export` в файлах, подключаемых тегом `<script>`.
25. **Тексты интерфейса и комментарии — на русском**, терминология — как в нормах (СП, ГОСТ), а не переводная. Имена файлов, веток, идентификаторов — латиницей.
26. **Доступность:** элементы управления — с подписями (`aria-*`), контраст в обеих темах, клавиатурная навигация не ломается. Новые экраны проверяются в светлой и тёмной теме и на ширине 390 px.
27. **Безопасность:** всё, что вставляется в DOM из данных, проходит `esc()` или строится через DOM API; SVG из `content/kb/fig` без скриптов и обработчиков (сборка проверяет); ключи доступа GitHub хранятся только в браузере пользователя, в репозиторий не попадают.

## 5. Порядок работы над задачей

```
Issue → план в комментарии к Issue → ветка → тест → код → build-content → npm test
→ CHANGELOG + версия → PR по шаблону → предпросмотр и контрольный расчёт заказчиком → слияние → тег
```

1. **Прочитать задачу и спорные места спросить до начала.** Непонятная задача не выполняется «как понял»; вопрос — в комментарии к Issue.
2. **План до кода.** Короткий план в комментарии к Issue: какие файлы, какие тесты, какой контрольный пример. Для задач больше одного файла — обязательно.
3. **Тест до кода** (п. 19).
4. **Сборка и тесты локально** (п. 20).
5. **PR по шаблону** `.github/pull_request_template.md`: что меняется, как проверить руками (конкретные шаги и ожидаемые числа), что не трогалось, конфликт интересов.
6. **Журнал работы.** Для задач длиннее одной сессии — файл `docs/worklog/<ветка>.md`: источники, решения, найденные противоречия, открытые вопросы (образец — `docs/worklog/wastewater-kb.md`).
7. **Завершение.** Заказчик принимает по сайту (предпросмотр ветки) и по контрольным расчётам. После слияния — тег и, если версия `0.X.0`, строка в «Что нового» на сайте.

## 6. Что агент делает в начале каждой сессии

1. `git status`, `git log -5`, текущая версия в `package.json`.
2. Прочитать Issue задачи и последний комментарий заказчика.
3. Прочитать `ARCHITECTURE.md` раздел о затрагиваемых файлах; `CONTRIBUTING.md`, если меняется контент.
4. Если задача касается расчёта — открыть источник (норму, ИТС) и выписать контрольный пример в план.
5. Назвать в первом сообщении: что будет сделано, какие файлы, какой тест, чего делать не будет.

## 7. Чего агент не делает никогда

- Не выполняет `git push --force`, не переписывает историю `main`, не сливает PR сам.
- Не меняет `LICENSE`, `LICENSE-CONTENT.md`, `CODEOWNERS`, `.github/workflows/*` без отдельной задачи от заказчика.
- Не добавляет внешние скрипты, шрифты, CDN, трекеры.
- Не публикует тексты норм вне правила 3 и тексты учебников сверх цитирования; не ставит ссылки на пиратские копии.
- Не удаляет пометки `[^?]`, `EST`, `≈`, `==…==`, не найдя источник.
- Не выдаёт свою оценку за данные источника.
- Не «улучшает» формулировки миссии, лицензий и правил этого файла.

## 8. Определение готовности (Definition of Done)

Задача закрыта, когда одновременно:

- [ ] критерии приёмки из Issue выполнены и проверены заказчиком на сайте;
- [ ] `npm test` зелёный, `build-content --check` чистый;
- [ ] у каждого нового числа и факта есть источник или честная пометка;
- [ ] версия поднята, `CHANGELOG.md` дополнен, тег поставлен;
- [ ] `ARCHITECTURE.md` и `README.md` отражают изменение, если оно их касается;
- [ ] журнал работы (если был) закрыт списком открытых вопросов;
- [ ] не изменено ничего, не названного в задаче.
