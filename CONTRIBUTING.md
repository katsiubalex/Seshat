# Как участвовать в Сешат

Сешат — открытая инженерная платформа водного хозяйства. Предложить правку может любой: студент, инженер,
преподаватель, сотрудник водоканала или производителя. На сайт правка попадает после двух проверок —
автоматической (тесты) и человеческой (куратор модуля или эксперт). Автор правки и проверяющий — всегда разные люди.

## Как предложить правку

1. **С сайта.** Под каждой статьёй, документом, курсом и мифом есть кнопки «Предложить правку» и «Нашли ошибку?».
   Выделите текст на странице до нажатия — он подставится в форму. Форма отправляется задачей на GitHub
   (поля заполнятся сами), письмом на katsiubalex@proton.me или копированием текста.
2. **Задачей на GitHub** — по шаблону «Правка или ошибка».
3. **В редакторе статей** на сайте (раздел «Редактор статей» на главной или кнопка «Править статью» под статьёй):
   статья открывается как текст, рядом — предпросмотр и проверка. Кнопка «Отправить на проверку» сама создаёт ветку,
   записывает файл и открывает запрос на слияние (pull request) — нужен только ключ доступа GitHub
   ([создать](https://github.com/settings/tokens/new?scopes=public_repo&description=%D0%A1%D0%B5%D1%88%D0%B0%D1%82):
   классический ключ с областью `public_repo`). У кого нет прав на запись, правка придёт из его копии (форка).
   Без ключа статью можно отправить письмом, скачать файлом или вставить на GitHub вручную.
4. **Сразу в исходниках** — если умеете работать с Git. Форма на сайте показывает файл и строку, где лежит материал;
   кнопка «Редактировать файл на GitHub» создаст копию репозитория и предложит отправить изменения (pull request).

## Правила качества

- **Источник у каждого факта**: пункт нормы, страница учебника, данные измерений, ссылка. Без источника правку не принимают.
- **Нормы не копируем**: ссылаемся на пункт и пересказываем своими словами. Файлы — только с официальных или легальных страниц;
  ссылки на учебники ведут к издателю, в магазин, электронную библиотеку или открытый текст, а не на агрегаторы.
- **Конфликт интересов раскрывается**: сотрудник производителя может предложить правку о своём оборудовании, но обязан это указать.
  Сравнения технологий — только по объективным критериям (НДТ, независимые данные); спонсорские материалы помечаются.
- **История открыта**: каждое изменение сохраняется в истории Git с автором и датой.
- **Актуальность**: раз в неделю автоматическая проверка ищет битые ссылки и документы, которые давно не сверяли
  (`tools/check-links.js`, задача «Проверка актуальности»).
- **Лицензии**: тексты и иллюстрации — [CC BY-SA 4.0](LICENSE-CONTENT.md), код — [MIT](LICENSE). Присылая правку,
  вы соглашаетесь, что она публикуется на тех же условиях; если вы оставили имя, оно сохраняется в истории правок.

## Статусы материалов

| Статус | Что значит |
| --- | --- |
| Черновик | Заготовка: программа или текст ещё не проверены. Сейчас так помечены курсы. |
| Проверено автоматически | Есть источники, ссылки и формат прошли тесты. Эксперт по существу ещё не смотрел. |
| Проверено экспертом | Материал проверил эксперт-рецензент; рядом указаны его имя и дата. |

Экспертные проверки записываются в `js/review.js` (`ITEMS`) отдельным изменением — не в том, в котором правился материал.

## Роли

| Роль | Кто | Что делает |
| --- | --- | --- |
| Читатель | Любой посетитель | Сообщает об ошибке кнопкой под статьёй |
| Автор | Студент, инженер, преподаватель | Предлагает правки и новые статьи с источниками |
| Эксперт-рецензент | Практик или преподаватель с подтверждённой квалификацией | Проверяет по существу, ставит отметку «Проверено экспертом» |
| Куратор модуля | Кафедра, лаборатория водоканала, проектный институт | Принимает правки модуля, назначает рецензентов, следит за актуальностью норм |
| Редакционный совет | 3–5 человек | Утверждает правила, разбирает споры, назначает кураторов |

Стать куратором или рецензентом — задача по шаблону «Стать куратором или рецензентом» или письмо автору проекта.
Кураторы записываются в `js/review.js` (`CURATORS`) и в `.github/CODEOWNERS` — тогда GitHub будет сам звать их проверять правки их модуля.

## Где что лежит

Статьи базы знаний и мифы — отдельные Markdown-файлы в `content/`: один файл — одна статья. Сайт читает их из
`js/content.js`, который собирается командой `node tools/build-content.js` (на GitHub — автоматически после слияния).
Формат файла: над чертой `---` поля статьи (`id`, `title`…), под ней — вводный абзац и разделы `## …`;
особые разделы «Уравнения», «Ключевые числа», «Источники», «Учебники», «Почитать» — списком `- …`.
Визуальный редактор для кураторов — Sveltia CMS (`/admin/`, настройки `admin/config.yml`, совместима с Decap CMS):
вход по ключу доступа («Sign In with Token»), каждая правка становится запросом на слияние. На своём компьютере —
«Work with Local Repository» в Chrome или Edge. После слияния GitHub сам пересобирает `js/content.js`
(`.github/workflows/content.yml`) и просит GitHub Pages обновить сайт.

| Материал | Файл |
| --- | --- |
| Модули: названия, что в них будет, дисциплины | `js/modules.js` |
| Сооружения очистки | `js/data.js` (расчёт), `js/plan.js` (как работает, размеры) |
| Процессы | `content/kb/processes/<id>.md` |
| Показатели качества воды | `content/kb/indicators/<id>.md` |
| Вспомогательные здания | `content/kb/aux/<id>.md` |
| Дисциплины «Основ» | `content/kb/fundamentals/<id>.md` |
| «Человек и вода» | `content/kb/humanities/<id>.md` |
| Учебники модулей, журналы, сообщества | `js/kb.js` |
| Методики измерений | `js/methods.js` |
| Учебники: где купить или прочитать | `js/books.js` |
| Нормативные документы | `js/docs.js` |
| Глоссарий | `content/glossary/<id>.md` — одно определение в файле |
| Курсы | `js/courses.js` |
| Мифы о воде («Гуманитарные аспекты») | `content/myths/<id>.md`, рисунки — `js/art.js` |
| Статусы, эксперты, кураторы | `js/review.js` |

## Проверка перед отправкой

```
node tools/build-content.js   # если правили файлы в content/
npm test
```

Тесты проверяют связность базы знаний, источники документов, методик и мифов, отсутствие пиратских ссылок и то,
что все страницы подключают файлы актуальной версии. Если меняли файлы в `js/` или `css/`, поднимите версию
в `package.json` и `version.json` и в адресах `?v=` на страницах — это проверяет тест `release`.
